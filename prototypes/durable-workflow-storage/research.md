## Cross-process suspend and resume

Mastra documents snapshots as persisted in configured storage when a step calls `suspend()`. In a fresh process, register the same workflow and storage, load state with `workflow.getWorkflowRunById(runId)`, then recreate the run with `workflow.createRun({ runId: state.runId })` and call `run.resume({ step, resumeData })`. For a generic recovery handler, `createWorkflowStateReader(state)` exposes the suspended step or resume label (including nested paths and `foreachIndex`) without parsing snapshot internals. [Suspend/resume guide](https://mastra.ai/docs/workflows/suspend-and-resume), [Mastra 1.74.0 recovery API source](https://github.com/mastra-ai/mastra/blob/a86dc424052b8dfbbf7eadb60a9c2acadbc0abc8/docs/src/content/en/docs/workflows/suspend-and-resume.mdx), [snapshot persistence guide](https://mastra.ai/docs/workflows/snapshots).

## Workflow storage concurrency

The beta.2 adapter's `updateWorkflowResults()` loads a snapshot, merges one result in JavaScript, then writes the whole `snapshot.results` map. Concurrent sibling writes can therefore race from the same old map and overwrite one another; `supportsConcurrentUpdates()` nevertheless returns `true`. The adapter tests cover snapshot persistence/upsert and assert that flag, but do not test concurrent result merging. [Adapter workflow implementation at the beta.2 release commit](https://github.com/surrealdb/mastra-ai/blob/bdbe769bcbf5eab23aa23e353d941591d249a4cc/src/domains/workflows/index.ts), [adapter beta.2 provenance](https://registry.npmjs.org/-/npm/v1/attestations/@surrealdb%2fmastra-ai@1.0.0-beta.2), [adapter workflow tests](https://github.com/surrealdb/mastra-ai/blob/bdbe769bcbf5eab23aa23e353d941591d249a4cc/src/tests/workflows.integration.test.ts).

There is also a distinct Mastra 1.74 storage-contract concern for the evented/partial-update path: core's `mergeWorkflowStepResult()` requires and updates `snapshot.context[stepId]`, and LibSQL 1.25.0 calls that helper inside a write lock and transaction; the Surreal adapter writes `snapshot.results` instead. Core documents `expectedStatus` as an atomic compare-and-set guard for stores claiming concurrent updates, while the Surreal adapter's `updateWorkflowState()` performs load/merge/upsert without applying that guard. The ordinary `.parallel()` API runs steps simultaneously, but this source mismatch concerns the WorkflowsStorage partial-update methods and should be assessed separately from full-snapshot default-engine runs. [Mastra 1.74.0 workflow storage source](https://github.com/mastra-ai/mastra/blob/a86dc424052b8dfbbf7eadb60a9c2acadbc0abc8/packages/core/src/storage/domains/workflows/base.ts), [Mastra 1.74.0 storage types](https://github.com/mastra-ai/mastra/blob/a86dc424052b8dfbbf7eadb60a9c2acadbc0abc8/packages/core/src/storage/types.ts), [LibSQL 1.25.0 workflow implementation](https://github.com/mastra-ai/mastra/blob/a86dc424052b8dfbbf7eadb60a9c2acadbc0abc8/stores/libsql/src/storage/domains/workflows/index.ts), [core provenance](https://registry.npmjs.org/-/npm/v1/attestations/@mastra%2fcore@1.74.0), [LibSQL provenance](https://registry.npmjs.org/-/npm/v1/attestations/@mastra%2flibsql@1.25.0), [parallel-step semantics](https://mastra.ai/docs/workflows/control-flow).

If the evented/partial-update path is in scope, the smallest public-contract check is to obtain `getStore('workflows')`, persist a valid `context` snapshot, run two `updateWorkflowResults()` calls for different step IDs concurrently, reload and assert both results exist under `snapshot.context`, then verify an `updateWorkflowState()` call with a nonmatching `expectedStatus` is a no-op. A full evented-engine run is broader; it is only needed if that execution model is required by the Factory.

## Supported fallback

If SurrealDB storage fails the required checks, `@mastra/libsql@1.25.0` is a compatible supported fallback: published 2026-10-01, it declares `@mastra/core >=1.68.0-0 <2.0.0-0` and Node `>=22.13.0`, which admit core 1.74.0 and Node 24.14.1. Mastra documents LibSQL workflow snapshot storage and a file-backed setup such as `new LibSQLStore({ url: 'file:./mastra.db' })`. [LibSQL 1.25.0 metadata](https://registry.npmjs.org/@mastra/libsql/1.25.0), [Mastra storage docs](https://mastra.ai/docs/storage), [snapshot provider docs](https://mastra.ai/docs/workflows/snapshots).
