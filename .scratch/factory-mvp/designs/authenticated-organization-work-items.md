# Authenticated, Organization-scoped Work Items

Status: Accepted by the User on 2026-10-03, including the concrete operation and persistence contracts. The live confirmation is recorded in [Create an authenticated, Organization-scoped Work Item](../issues/02-authenticated-organization-work-items.md#comments). No production code or delivered acceptance check exists yet. The alternatives and historical proposal wording below describe the design that was confirmed, not unresolved product decisions.

## Goal and boundary

Deliver one usable path: authenticate, access an explicitly provisioned Organization or activate its Invitation, create a Work Item, and inspect or extend its persistent immutable Fact history through the UI and public API. Provide Organization-scoped API credentials and recoverable protection for stored secrets.

TanStack Start owns the application and API. SurrealDB stores Factory data. Authentication uses one installation-configured OIDC provider; the Factory owns Users, Memberships, and authorization. Retain the accepted separate Mastra worker architecture, but do not start Workflow Runs in this increment. Prototype manifests and dependencies remain isolated.

Organizations, Projects, optional Repositories, initial Memberships, and initial permission grants are explicitly provisioned by an operator through an idempotent installation command. Provisioning is not an unauthenticated HTTP endpoint. Subsequent Invitations require Factory permission; automatic email delivery and Organization-level federation configuration are outside this increment.

## Considered operation boundaries

1. **Recommended: shared server-only Factory operations.** Protected UI server functions and public HTTP routes call the same operations, which validate authentication, authorization, ownership, and atomic persistence. This fits TanStack Start and prevents two divergent rule implementations.
2. **Alternative: UI calls only the public HTTP API.** This reduces the number of entry-point adapters but makes browser sessions and external API credentials share a larger HTTP interface. It remains viable, but does not remove the need for shared authorization and transaction rules.

The remaining design uses the first option. Database credentials and secret-decryption capabilities are never exposed to the browser or API caller.

## Identity and browser sessions

- Configure a trusted OIDC issuer, registered client, callback URI, and required client-authentication settings per installation. Use Authorization Code Flow with PKCE (`S256`), validate issuer/audience/signature/token lifetime, and protect the login transaction against replay and request substitution. Provider discovery is configuration lookup, not client registration.
- Resolve a User by the exact (`issuer`, `subject`) pair with a unique database constraint. First valid authentication creates that User at most once. Store email and provider verification status as contact attributes; email is not a User identity key and never merges accounts.
- A new User has no Membership or Activity permission. The UI exposes an authenticated no-access screen until explicit provisioning or authorized Invitation activation establishes access.
- Use an opaque server-side browser session with a hashed stored identifier, a secure HTTP-only cookie, and a proposed maximum lifetime of 12 hours. Require a fresh login to renew it. Destroy the server-side session at logout. Protect browser mutation operations against cross-site requests.
- Read current Membership and permission data on every authorized operation. A still-valid session is not a cached authorization grant. Membership revocation takes effect for subsequent operations without waiting for session or API-credential expiry.
- Accept verified email evidence only from the configured trusted issuer under a documented provider contract. Missing or false email verification rejects Invitation activation while ordinary valid login can still produce a no-access User. Changing providers requires an explicit migration; no automatic account-linking tool is introduced here.

## Persistence records and invariants

Use schema-validated SurrealDB records and unique indexes. Record identifiers are generated by the Factory. API inputs cannot select the actor identity, create authoritative provider observations, or override Factory-managed history fields.

| Record | Required contents and constraints |
| --- | --- |
| User | Factory identifier, exact issuer/subject pair, contact attributes, creation time; unique issuer/subject pair |
| Browser session | Identifier digest, User, issued/expiry times, revocation state; no plaintext cookie value stored |
| Organization | Identifier, display name; created through explicit operator provisioning |
| Project | Identifier, owning Organization, display name |
| Repository | Identifier, owning Project, display name, optional provider locator; Organization derived and checked through Project |
| Membership | User, Organization, active/revoked state; unique User/Organization pair; stored independently for each Organization |
| Permission policy | Owning Organization, principal/scope, Activity, allow/deny/human-intervention rule; no cross-Organization principal or scope reference |
| Work Item | Identifier, Organization, Project, optional Repository, title, type identifier, retained state-flow version, initial/current Factory state, creation actor/time |
| Fact | Identifier, Work Item, Organization, kind, typed payload, authenticated actor, recorded time, optional corrected-Fact reference; no Factory update/delete operation |
| Invitation | Organization, intended email, proposed initial grants, issuing User, token digest, issued/expiry times, revoked/consumed state, consuming User/time |
| API credential | User, one Organization, label, token digest, maximum Activity scope, issued/expiry times, revocation state; plaintext token returned once |
| Stored secret | Owning scope, purpose, ciphertext, nonce/authentication metadata, encryption-key identifier; purpose and ownership bound into authenticated encryption |
| Operation receipt | Organization, User, operation, client operation identifier, request digest, result reference; unique per operation identity |

Referential validation and writes run in the same database transaction. A Project/Repository mismatch or a record from another Organization cannot be accepted merely because the caller knows its identifier. Transaction failures commit neither a partial business change nor a misleading successful Fact/receipt.

Work Item creation stores its initial Fact atomically with the Work Item. Fact correction appends a new typed Fact referencing an existing Fact on that same Work Item; the original remains readable.

The application database account is server-only. This immutability contract applies to Factory operations; privileged database administration and restore are operational authority, not public history-editing operations.

## Initial Work Item Type

Propose one minimal platform-owned `pull-request-review` definition, state-flow version `1`, with initial state `registered` and no exposed State Transitions. A Work Item of this type can exist without any external pull request. Users select an available type but do not supply arbitrary state or version values.

[Execute authorized Transition Requests from the Kanban Board and API](../issues/03-authorized-transition-requests.md) owns the actual review lifecycle, transitions, Teams, and Approval behavior. It must not reinterpret already retained definitions; new behavior uses explicitly versioned definitions, with migration behavior owned by the existing version-retention ticket. The initial version remains available for existing Work Items. No Kanban transition or Workflow launch is implied by creation here.

## Activity authorization

For this increment expose Activity permissions for Work Item create/read, history read, manual note append, correction append, external-reference append, Invitation issue/revoke, and API-credential issue/revoke. Invitation grant delegation requires an explicit permission to delegate the requested grant; invitation permission alone is insufficient.

Evaluate active Membership plus applicable Organization, Project, Repository, and User policies; deny by default, inherit grants, and let explicit prohibitions prevail. Reject an automatic caller where an applicable policy requires human intervention. Browser authentication or an API credential supplies identity, not permission.

Teams and transition-bound Approval management are delivered by the existing transition ticket; do not claim this increment implements that broader policy UI. Keep authorization inputs compatible with evaluating all associated Teams when that capability is introduced. No predefined administrator role silently bypasses prohibitions. Operator bootstrap explicitly installs grants and delegation authority for the initial Users.

For an API caller, effective access is the intersection of the credential's Organization/Activity scope and the User's current permissions. API credentials cannot perform browser-only human-confirmation operations, including Invitation activation. A User issues credentials only for their own active Membership. Separate permission governs issuance; issuing credentials for another User is not part of this increment.

## Invitation contract

1. An authenticated User with current issuance and delegation authority creates an Invitation for one Organization, intended email, and explicit initial grants. Default expiry is 7 days, configurable by installation. Return a shareable link once and persist only its token digest.
2. Opening the link begins an explicit accept flow. Show the Organization and proposed access; authenticate through the configured issuer if needed. A GET or login callback alone never consumes the Invitation or grants access.
3. An authenticated browser confirmation validates token, expiry, revocation, matching verified email, and current issuer delegation authority. Re-evaluate the issuer's Membership and grant bounds at activation; if authority was removed or a prohibition now applies, reject activation without granting access.
4. Atomically create the recipient Membership/grants and consume the Invitation. A concurrency check permits at most one successful consumption. Retrying the same completed activation for the same recipient returns the prior operation outcome and never re-grants subsequently revoked access.
5. A pre-existing active Membership is not silently overwritten or extended by an Invitation. Reject activation as already a member; changing that Membership's permissions requires explicit authorized management. A revoked Membership may be reactivated only by an Invitation issued after its latest revocation and valid at activation; older Invitations cannot undo revocation.
6. Cross-Organization grants, mismatched email, missing verified email, expired/revoked links, consumed links belonging to a different User, or insufficient delegation authority have no Membership side effects.

Preserve the issuing and consuming actors and their relevant decisions in append-only onboarding audit records. These are not Work Item Facts because an Invitation has no Work Item owner. Do not log token values.

## Public operation contracts

All domain mutations validate input before entering their transaction and require a caller-generated operation identifier. Repeating the same operation identifier and request returns the same recorded outcome without duplicate business records/Facts. Reusing it with different content is a conflict. Domain failure records no successful receipt. Reads are paginated with stable cursors.

| HTTP operation | Inputs and visible result |
| --- | --- |
| `GET /api/organizations` | Caller identity; return only Organizations with active Membership and permitted visibility |
| `GET /api/organizations/{organizationId}/projects` | Authorized Organization scope; return permitted Projects and Repository selections |
| `POST /api/organizations/{organizationId}/work-items` | Operation identifier, Project, optional Repository, title, available type; atomically return the created Work Item and initial Fact |
| `GET /api/organizations/{organizationId}/work-items/{workItemId}` | Authorized scope; return retained type/version, stored Factory state, and ownership |
| `GET /api/organizations/{organizationId}/work-items/{workItemId}/facts` | Authorized scope, cursor/limit; return immutable history without secrets |
| `POST /api/organizations/{organizationId}/work-items/{workItemId}/notes` | Operation identifier and note text; append an actor-attributed manual note Fact |
| `POST /api/organizations/{organizationId}/work-items/{workItemId}/corrections` | Operation identifier, existing Fact identifier, correction text; append a correction Fact, preserving the original and its source |
| `POST /api/organizations/{organizationId}/work-items/{workItemId}/references` | Operation identifier, provider, canonical external locator; append a reference Fact without claiming primary resource correspondence |
| `POST /api/organizations/{organizationId}/invitations` | Authorized issuer, operation identifier, intended email, initial grants; return Invitation metadata and link once |
| `POST /api/organizations/{organizationId}/invitations/{invitationId}/revoke` | Authorized issuer/revoker and operation identifier; reject later activation |
| `POST /api/invitations/accept` | Authenticated browser confirmation, operation identifier, Invitation token; return Membership activation outcome |
| `POST /api/organizations/{organizationId}/api-credentials` | Browser session, operation identifier, label, narrower Activity scope, expiry; return credential metadata and token once; maximum lifetime 90 days, installation-configurable |
| `POST /api/organizations/{organizationId}/api-credentials/{credentialId}/revoke` | Browser session, own credential, required permission, operation identifier; revoke future use |

API credentials authenticate public API calls as opaque bearer tokens. Store only cryptographic token digests, so these one-way-verifiable tokens do not require recoverable storage in the key ring. Limit credential creation/revocation to authenticated browser sessions to prevent an API credential from creating replacements for itself.

Secret-bearing responses are a deliberate exception to replaying response bodies: never persist a plaintext Invitation/API token in an operation receipt. A retry of issuance returns the prior resource metadata and indicates the secret is unavailable; the User must explicitly revoke and issue a new resource if the first response was lost. A retry must not create a second live resource automatically.

Return `401` for missing/invalid/expired/revoked authentication, `403` for a denied Activity in a visible scope, `404` for missing or cross-Organization resources, `409` for operation-identifier mismatch, consumed/conflicting activation, or invalid ownership relationship, and `422` for invalid input. Do not reveal another Organization's record existence through detailed errors. Never expose stored ciphertext or key material through ordinary reads.

Manual public operations cannot impersonate provider/agent evidence, confirm Findings, append State Transition Facts, or alter current Factory state. A correction records a User's correction text; it does not erase or manufacture a provider observation. Provider ingestion belongs to its existing ticket.

## Minimal UI

Provide login/logout, the authenticated no-access screen, Organization selection, Work Item creation with Project/optional Repository/type selection, and Work Item detail with Factory state and paginated Fact history. Authorized Users can add notes, corrections, and external references.

Provide explicit Invitation preview/accept, authorized issuance with a copyable link, and self-owned API-credential creation/revocation with one-time token display. Do not add a Teams/policy editor, state-transition board, federation editor, email service, or generic secret-management UI.

## Key-ring protection and recovery

The application generates versioned encryption keys and persists the encrypted key ring in a dedicated volume. A separately supplied deployment root key protects that ring. Use a maintained authenticated-encryption primitive with Organization/purpose binding, independent fresh nonces, and explicit key identifiers; do not invent a cryptographic algorithm.

Preserve needed keys across restart and rotation. Use one authoritative writer for ring changes; a stale web/worker process must not activate an unverified generation. Reject corrupted/missing keys or wrong installation/root protection without silently regenerating keys over stored data. First setup is explicitly distinguishable from recovery.

Deliver a protected export, a verified configurable external backup destination, and a manual restore path in this increment. Verify the backup before activating any new key generation. The [key-ring backup and recovery plan](../../../docs/operations/key-ring-backup.md) specifies the accepted daily database backups, minimum 30-day retention, monthly restore drills, and separate root-key custody. The installation ticket owns production scheduling, monitoring, and the measured restore objective.

The OIDC client bootstrap and database credentials require a documented deployment configuration path before encrypted database-managed secrets can be used. Do not introduce a circular dependency in which recovery credentials are available only through the installation being recovered. Operator configuration and the root-key file/secret are not committed to Git or container images.

## Verification

The primary checks exercise public Factory operations with a real persistent SurrealDB process and the TanStack Start server. Use a controlled standards-conforming OIDC boundary to verify error cases and a self-hosted OIDC provider for one real login/create/history scenario. Pin supported runtime/package versions during implementation after current official API verification; prototype dependency pins do not automatically become production dependencies.

| Scenario | Required observed outcome |
| --- | --- |
| New valid login and repeated login | One stable User; no automatic Organization access or duplicate User |
| Same email, different issuer/subject | Separate Users; no shared Memberships or automatic merge |
| Two Organizations and independent Memberships | Only authorized records visible; mismatched Project/Repository rejected |
| UI versus bearer-token API | Same ownership/domain rules; token limited to one Organization and allowed Activities |
| Credential expiry, revocation, Membership revocation | Subsequent requests denied without waiting for a new login |
| Work Item create and interrupted transaction | Exactly one Work Item/initial Fact/receipt on success; no partial success on failure |
| Repeated/changed operation identifiers | Same result without duplicate Facts, or a conflict when content differs |
| Manual note/correction/reference | Actor-attributed append-only history; original Fact retained; no primary provider-resource claim |
| History manipulation and forged evidence | No update/delete operation; impersonated authoritative Fact kinds/state changes rejected |
| Invitation activation and concurrent accept | Matching verified recipient and explicit confirmation; one Membership activation |
| Invalid Invitation or revoked issuance authority | No Membership/grant side effects |
| Already-active or subsequently revoked Membership | No silent grant replacement; stale Invitations/retries cannot restore revoked access |
| Process/database restart | Stable Users, Memberships, ownership, Work Items, Facts, credentials, and secret decryptability |
| Ring rotation and compatible older backup | Both required key versions restore and decrypt correctly |
| Missing/wrong/corrupted keys or failed backup | Explicit error; no silent key replacement or new-key activation |

Do not mark acceptance criteria complete on the basis of this design, a unit-test-only substitute, or storage-prototype evidence. The issue closes only when its own public-flow and restore checks pass and the implementation is reviewed.
