# Mastra Docker sandbox contracts

## Evidence boundary

The prototype lockfile pins `@mastra/core` to `1.74.0` ([lockfile](../../../prototypes/durable-workflow-storage/package-lock.json)). Its installed dependencies do not include `@mastra/docker`. At the same Mastra source commit used to check the core pin ([`b21e46e`](https://github.com/mastra-ai/mastra/tree/b21e46e19b469a25c8896bcee90afd58d6f1a890)), the official [`@mastra/docker` manifest](https://raw.githubusercontent.com/mastra-ai/mastra/b21e46e19b469a25c8896bcee90afd58d6f1a890/workspaces/docker/package.json) is version `0.9.2` and declares peer `@mastra/core >=1.67.0-0 <2.0.0-0`, which includes `1.74.0`. This is declared compatibility evidence, not a tested import or runtime integration. No dependency was installed and Docker was not run. Current Mastra docs likewise prescribe `@mastra/docker` and a Docker Engine running on the host ([Docker integration](https://mastra.ai/integrations/sandboxes/docker)).

## Pinned adapter and filesystem contract

The adapter exports `DockerSandbox` from `@mastra/docker`; it is passed as the `sandbox` to `Workspace` from `@mastra/core/workspace`. The pinned [`DockerSandbox`](https://raw.githubusercontent.com/mastra-ai/mastra/b21e46e19b469a25c8896bcee90afd58d6f1a890/workspaces/docker/src/sandbox/index.ts) uses long-lived containers and `docker exec`; the default image is `node:22-slim`, the command keeps the container alive with `sleep infinity`, and its working directory defaults to `/workspace`. It supports `start`, `stop`, and `destroy`; `start` reconnects to an existing container with the same sandbox ID. The `volumes` and `mounts` options can bind host paths, and `writeFiles` uploads into the container.

Mastra's pinned [`WorkspaceSandbox` interface](https://raw.githubusercontent.com/mastra-ai/mastra/b21e46e19b469a25c8896bcee90afd58d6f1a890/packages/core/src/workspace/sandbox/sandbox.ts) allows the sandbox filesystem to differ from the Workspace filesystem. At this pin, `DockerSandbox` implements file upload and Docker bind mounts, but not the generic `mount(filesystem, path)` method. Therefore a host `LocalFilesystem` must not be assumed to appear inside the container. Current docs describe FUSE mounts only for sandbox providers that support mounting ([sandbox overview](https://mastra.ai/docs/sandbox/overview)).

For this MVP, keep the repository checkout inside each container and give the agent platform-authored Git, read, and search tools that route to that run's sandbox. The tools should use fixed executables and validated operations and paths; do not expose Mastra's generated arbitrary `execute_command` tool or raw Docker client/container access to the agent. If Workspace-generated tools are used, disable the default set and explicitly enable only the required capabilities. The pinned adapter's [`DockerTemplate` and repository-template README](https://raw.githubusercontent.com/mastra-ai/mastra/b21e46e19b469a25c8896bcee90afd58d6f1a890/workspaces/docker/README.md) documents `createDockerRepoTemplate`, credential-aware checkout preparation, and fresh containers with independent writable layers over a reusable image. The README also warns that build-time secrets must not be baked with `setEnvs`; its secret flow exposes them only to a BuildKit build step, not the agent container. Include Git and the chosen search utility in a reviewed image; the default image is not a promise that those tools exist.

## Run isolation and application responsibilities

Assign each Workflow Run a unique sandbox ID so one run cannot reconnect to another run's container. Reuse that ID only when resuming the same run; destroy its container at terminal cleanup. A reusable template image can seed new containers, but it is distinct from each run's mutable filesystem. The repository template resolves and pins a ref to a commit for its image identity, allowing a later run to rebuild from changed repository state.

The adapter defaults `privileged` to `false`, but CPU, memory, PID, root-filesystem, capabilities, security options, and network policy are not automatically constrained. Configure these through the adapter's Docker options and validate them against the deployment's Docker Engine. Keep daemon access (`dockerOptions`, socket, or TLS credentials) in the trusted platform process; never mount a Docker socket into the sandbox or expose DockerSandbox's underlying container handle as an agent tool. Prepare private checkouts with platform-controlled credentials and do not put tokens in container `env`, agent context, or the reusable image. Runtime creation, path access, tool restrictions, and cleanup still require integration validation at the selected versions.
