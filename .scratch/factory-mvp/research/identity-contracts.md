**Purpose:** Background facts for the selected Factory MVP ticket. This note records standards and product capabilities; it does not settle Factory policy or architecture.

## OpenID Connect client and identity mapping

A relying party can start with a configured OpenID Provider (OP) issuer and retrieve its metadata from the issuer's `/.well-known/openid-configuration` URL. The metadata supplies endpoint and capability information, including issuer, authorization and token endpoints, signing-key location, supported response types, and supported token-endpoint authentication methods. The metadata's `issuer` must match the issuer URL used to retrieve it, and that issuer must match the `iss` claim in ID Tokens. [OpenID Connect Discovery 1.0](https://openid.net/specs/openid-connect-discovery-1_0.html)

Discovery does not itself provision a client. OpenID Connect Core assumes the relying party has already obtained the provider configuration plus sufficient client credentials and registration information. Client registration can be static/preconfigured or use the separate Dynamic Client Registration specification. Core says preconfigured relationships may not need discovery or dynamic registration; for unanticipated RP/OP relationships it recommends the Discovery and Dynamic Registration facilities. Therefore an installation-configured generic client still needs a provider trust decision and a client registration/credential exchange with each OP, unless the deployment supplies those through another agreed mechanism. [OpenID Connect Core, §§1 and 15.3](https://openid.net/specs/openid-connect-core-1_0.html)

For a web relying party, the Authorization Code Flow uses `response_type=code`; OAuth Security BCP RFC 9700 recommends the code response instead of implicit responses that expose access tokens in the authorization response. Public authorization-code clients **MUST** use PKCE; confidential clients are **RECOMMENDED** to use it. Clients should use a PKCE method that does not expose the verifier; RFC 9700 identifies `S256` as the only such method at publication. Authorization servers must support and enforce PKCE. Registered redirect URIs are matched exactly, subject to the RFC's localhost native-app port exception. A client talking to multiple authorization servers also needs a mix-up defense. [RFC 9700, §§2.1–2.1.2](https://www.rfc-editor.org/rfc/rfc9700.html)

For Factory's durable external account mapping, OpenID Connect Core identifies the exact pair **(`iss`, `sub`)** as the only claims an RP can rely on as a stable identifier for an End-User. `sub` is locally unique and never reassigned within its issuer. Other claims, including email, may change or be reused and **must not** be used as unique identifiers. A provider may use pairwise subjects, which differ by client, so subjects should not be assumed to correlate across clients. ID Tokens must be validated, including exact issuer matching and an audience containing the configured `client_id`. [OpenID Connect Core, §§3.1.3.7, 5.7 and 8](https://openid.net/specs/openid-connect-core-1_0.html)

The `email_verified=true` claim means that the OP took affirmative steps to establish control of that email address **at the time of verification**. The verification method and whether another party should rely on it are context-specific and depend on the parties' trust framework or contracts. OpenID Connect does not say this claim identifies the person intended by a Factory invitation, guarantees current control of the address, or establishes the user's intent to join a particular Factory Organization. **Inference:** `email_verified` may be useful contact evidence under a trusted OP relationship, but by itself it does not prove that a current login is the intended holder of a pending invitation. [OpenID Connect Core, §5.1 and §5.7](https://openid.net/specs/openid-connect-core-1_0.html)

## Keycloak capability versus Factory scope

The current Keycloak 26.8.0 Server Administration Guide documents organizations with one or more linked identity providers, identity providers shared across organizations with separate per-organization link settings, domain-based routing, and optional automatic membership. It also documents a mode where an identity provider is linked for login convenience while membership is handled through invitations or manual administration. These are capabilities of Keycloak's organization feature and identity broker. [Keycloak Server Administration Guide 26.8.0, “Managing identity providers” and “Common setup recipes”](https://www.keycloak.org/docs/26.8.0/server_admin/)

This capability does not imply that Factory must implement organization-level federation in the MVP. That is a product-scope decision. The repository context also defines a Factory **Organization** as an independent customer boundary and says a provider's organization is not automatically equivalent to a Factory Organization. Keycloak's feature demonstrates that federation can support richer membership policies; it does not establish that those policies are required now.

## Persistent application-managed key ring in a Node runtime

Node's crypto documentation describes `KeyObject` as an **in-memory representation** of a parsed key. Node supports importing and exporting keys (including encrypted private-key export with a passphrase), but its crypto API does not provide an application-level persistent key ring, storage lifecycle, backup policy, or cross-restart recovery mechanism. **Inference:** any key ring expected to survive process restarts must persist its key material or a means to reconstruct it outside the in-memory `KeyObject`; if several application instances need to decrypt the same durable data, they need access to compatible key versions. [Node.js Crypto API](https://nodejs.org/api/crypto.html)

OWASP key-management guidance treats storage, rotation, backup/recovery, and destruction as lifecycle responsibilities. It says keys should not be committed to source or build artifacts, should not be stored in plaintext, and should be protected in persistent as well as volatile memory. For offline/database storage, it describes encrypting key material with a separate key-encryption key (KEK), with equivalent or greater strength, and integrity protection. The OWASP Cryptographic Storage guidance says rotation can either decrypt and re-encrypt existing data or retain multiple keys and identify which key encrypted each item; retired keys may need to remain available so older backups can still be decrypted. [OWASP Key Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet) · [OWASP Cryptographic Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html)

NIST SP 800-57 Part 1 Rev. 5 separates operational storage, backup, archive, and recovery. It says recoverability is an application-specific decision; if key material must be recoverable, it should be backed up, archived, or reconstructible. Backup material should be held in independent secure storage and at least as long as the corresponding key remains in operational use. For protected data that must remain decryptable, the associated decryption key must also remain recoverable for the relevant period; losing the key prevents recovery of the plaintext. NIST also says a key should be destroyed once it is no longer needed. OWASP adds the practical rotation case where old backups may need retired keys. Together, these sources do not prescribe a fixed retention period: it depends on the protected data's lifetime, backup/restore window, key purpose, and recovery policy. [NIST SP 800-57 Part 1 Rev. 5, §§8.2.1–8.2.2 and Appendix B](https://doi.org/10.6028/NIST.SP.800-57pt1r5) · [OWASP Cryptographic Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html)

## Product questions left open

- Is an OP configured once for an installation, per Factory Organization, or at another scope? Which administrator can designate a trusted issuer, and is a generic client registration pre-provisioned or performed dynamically?
- Which authentication and client-authentication methods must the supported OPs provide? How are client credentials stored and rotated? Which exact redirect URI does each installation register?
- How are identities from different (`iss`, `sub`) pairs treated: separate accounts, explicitly linked accounts, or another policy? Is any identity auto-added to a Factory Organization, or does membership require an invitation or administrator action?
- What evidence is required to accept a pending invitation? What is the policy for address changes, reused addresses, unknown or untrusted issuers, and missing `email_verified` claims?
- What purpose does the key ring serve (for example, encryption, authentication, or signing), what data does it protect, and how long must that data remain usable? The key purpose affects key type, key separation, retention, rotation, backup, and recovery requirements.
- Must recovery cover process restarts, instance replacement, disaster recovery, and restoration of old data backups? What storage, wrapping-key custody, recovery access, and retention policy will meet that requirement?

These questions require Factory product and operational decisions. The standards and vendor documentation do not answer them for Factory.
